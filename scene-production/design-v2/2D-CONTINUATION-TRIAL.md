## 本轮解决的实际问题

长直道会同时暴露过多重复岩片和未组织的远端。增加图片变体不能单独解决视线长度。这里在战斗保留区之后编译一个可真正走完的有限弯道：先侧向偏移，再回到所选通道既有轴线。左右分支保留原有横向位移，不永久斜向发散，也不把角色拉回主干中央。

弯道起点 51m、峰值位置 65m、回正位置 79m 是本候选的事件节奏，不是所有洞穴的统一常数。编译器拒绝弯道与战斗展示保留区相交。

比较了 2.4m / 3.2m / 4m 三种偏移。相同战斗观察点的 180×100 离线测量中，背景分别残留 1 / 0 / 0 像素，轴向视线首次命中结构的距离约 28.33 / 24.82 / 24.82m。3.2m 用更小的位移达到与 4m 相同的这项结果，因此用于实际试验。**单视点测量不是整体好看的证明。** 原始比较保存在 `continuation-comparison.json`。

## 路线、地面、图片共用数据

`tools/compile_cave_continuation.py` 编译：

- 完整图片在世界中的平移；不改变图片比例、固定朝向或像素。
- 每条分支 257 个样本，每行是 `[横向位置, 相对前进位置, 累计弧长, 切线角]`，位置和弧长以米计。运行时统一乘 20 转换为原工程单位。
- 左、右、中路独立样本，不能把中路永久写死为直线。
- CPU 行进按累计弧长采样。地面 shader 读取同一张三行查找纹理，不能自行再写另一条多项式。
- 悬挂组按父件的位置整体平移，不能分别沿曲线挪动父子而破坏吊点。
- 编译到 116m 的前向结构缓冲，在 80m 起与原段重叠。第一轮只保留到 82m，导致相机走至 79m 时结构缓冲不足，已作为失败记录保留。**这段缓冲不是无限路段加载器，也不是终点处理完成。**

实现：`godot/tests/fixtures/cave_cards_sampled_route.gd`、`godot/scripts/world3d/ground.gdshader`。老的单条对称曲线继续使用原单行纹理；多行模式仅由具备对应方法的曲线启用。普通森林没有启用这条研究曲线。

## 为什么还需要独立镜头轨迹

第一轮实际行进暴露了新问题：角色站在镜头前方 1.6m，弯道上脚下路线与前方角色的横向位置不同，角色被挤向边缘。几何不穿插检查没有发现这个构图错误。

修正使用原 `travel_rig.gd` 的前方距离，不新造人物占比参数：

1. 行进路线提供当前累计路程对应的位置。
2. 取前方 1.6m **弧长**处的路线横向位置，作为镜头的横向目标。
3. 保持原镜头前进位置、朝向、镜头参数和高度。既有镜头平滑器跟随这条目标轨迹。
4. 在弯道尚未开始但前方角色已接近弯道时自然开始横向跟随；不能在跨过某个开关点后突然补位。
5. 这条镜头轨迹必须回到结构覆盖检查中；不是图片生成完后无限制移动相机。

正式路线默认仍返回原路线位置；研究夹具通过 `presentation_route_position()` 覆盖。没有把自由旋转/缩放相机加入游戏。

新增 `tools/audit_cave_travel_composition.py`：使用进入岔路前的实际角色根节点画幅横坐标为基准，检查后续弯道。研究容差是画幅宽的 4%，不是全项目美术标准；岔口主动收拢队形不属于这项检查。原失败版本最大偏离约 28.35%；修正后左路约 3.39%、中路约 3.24%。原失败版本已被该检查拒绝，不能继续拿早期根包络通过标签当作交付证明。

## 复现

```text
F:/python/python.exe tools/compile_cave_continuation.py --spec <cards-fork-event-fit-02/fork.json> --offset 3.2 --out <新目录>
F:/python/python.exe tools/run_cave_cards_study.py --godot <Godot console> --spec <新目录/fork.json> --branch=-1 --continuation-probe --out <新捕获目录>
```

中路使用 `--branch=0`。战斗入场使用 `--event-probe`，不能与 `--continuation-probe` 同用；前者只验证入场和两秒战斗，后者无战斗地验证整段行进。二者不是一个完整的战斗结束、继续行进的流程。
